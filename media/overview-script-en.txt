Agent Harness Kit.

Agent Harness Kit is a single, platform-agnostic development harness that helps coding agents work with durable context, clearly defined roles, dependency-aware tasks, isolated environments, independent review, and reproducible evidence.

Native support for both tools is built in: Codex enters through A G E N T S dot markdown, Claude Code through CLAUDE dot markdown, and both use the same neutral core.

On a new context window, resume request, or status request, the agent must read the approved project context first, PENDING dot M D second, and TASK GRAPH dot M D third. PENDING owns human decisions, human actions, and the macro view of unfinished project areas such as backend or authentication. TASK GRAPH owns technical order, dependencies, and execution. Every status must show stage, progress, blockers, next action, and inspectable paths. It may scan more broadly only when those artifacts reveal a concrete gap or the user explicitly requests an audit.

To control cost without silently reducing quality, tasks are routed by capability. Economical models are limited to narrow mechanical work with deterministic checks. Balanced models are the normal default for bounded implementation, tests, documentation, and inspection. Frontier models are reserved for architecture, security, brainstorming, difficult integration, harness evolution, and repeated failure. Model choice never grants extra permission.

Each task also carries an executable goal-lineage budget. By default, an agent may make at most two implementation attempts, spend at most two consecutive cycles without measurable progress, and expand context at most three times. Changing the model, agent, task, review, decomposition, or session does not reset those counters. When any ceiling is reached, the agent must record evidence, stop, and return the work for bounded replanning instead of consuming more context.

It works for both new projects and mature repositories that already have Claude context, Codex instructions, agents, rules, or a custom harness. In those repositories, it does not overwrite anything immediately. It first inventories and freezes existing authorities. It then installs through staged coexistence in a separate namespace and requires human review before anything is removed or replaced. The README also links to the migration and coexistence playbooks and contracts.

There are three options.

Core is for development only.

Core Learning adds learning based on the current project.

Full also includes a separate, optional pack for studying harness engineering.

All three packages are generated from the same source. Installing an option that contains learning features does not grant consent or activate anything automatically.

On first use, if the project has no approved context, the agent starts an adaptive interview. It discovers what already exists and asks only for missing information. The user may also request a plain-language explanation of Agent Harness Kit and what will happen in the project, without activating any learning mode.

After the interview, the user reviews the project context, selects the working mode, and approves important decisions. The system creates the task graph. Each specialist receives a bounded task and exclusive file ownership. When declared checks pass, the orchestrator marks the task completed, reports what changed, releases ownership, and starts the next ready task without asking for completion approval.

Reviews are independent, automatic, non-blocking assurance. Each completed task receives one risk-proportional initial review and, only when a blocking defect exists, at most one focused remediation review of prior blockers, correction delta, and related regressions. Optional improvements become follow-ups. A blocker creates a linked remediation task and may gate only affected integration or release work; it does not reopen completed history or stop unrelated ready tasks. A second rejection forces rewrite, decomposition, or a genuine human product or risk decision. There is no third review loop.

Related microcorrections are grouped into one coherent, reversible change when they share acceptance and rollback boundaries. Changes are split only for meaningful ownership, deployment, dependency, risk, review, or rollback boundaries. Technical acceptance does not automatically authorize a commit, push, deployment, or publication.

Here are a few examples.

If you want to build a platform from scratch and learn the technologies while building it, use Core Learning. The kit helps discover the product, organize context, create the task graph, and turn real project decisions into guided practice.

If you already know the stack and only want more organized and verifiable agent-assisted development, use Core.

If your repository already has Claude context, Codex instructions, or a custom harness, the kit can enter through coexistence. It preserves what already exists, records the source of every material item, and allows cutover only after human review.

Agents are editable as well. During discovery, the kit identifies the specialties the project needs and helps adapt or create roles, responsibilities, tools, and review criteria. You can customize the team without changing the harness core, provided that authority boundaries and verification remain explicit.

Tools include native agent capabilities, MCP servers, skills, scripts, hooks, and integrations. Discovery identifies which capabilities are actually needed, which are already available, and which require installation or authorization. The kit never assumes access that has not been confirmed.

Users may also define business, security, architecture, style, and path-scoped rules. The harness organizes those rules in a dedicated area, routes each rule only to relevant agents and tasks, and preserves rules that already exist in the project.

If your goal is to study harness engineering itself, use Full and open the separate learning pack without loading that material into operational project work.

Today, Agent Harness Kit already provides the operating structure, contracts, agents, templates, playbooks, capability-based model routing, bounded execution budgets, coherent change integration, validation, and packaging. It is not yet a standalone program that automatically dispatches agents, creates worktrees, and integrates branches on every platform.
